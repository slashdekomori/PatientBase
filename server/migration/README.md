# Переход со старой версии PatientBase (SQLite → PostgreSQL)

Старые версии программы хранили случаи в файле `DataBase.db` (SQLite). Начиная
с версии с сервером PostgreSQL данные лежат в таблице `database` на сервере.
Этот раздел описывает перенос случаев из старого файла в базу отделения.

Перенос делается один раз при переходе отделения на новую версию. После переноса
старый `DataBase.db` больше не нужен, но удалять его стоит только после проверки
и бэкапа.

## Что понадобится

- старый файл `DataBase.db` (обычно лежит рядом со старым `PatientBase.exe`);
- Python 3 на любой машине (на сервере или на рабочем месте) — только стандартная
  библиотека, ничего устанавливать не нужно;
- доступ к серверу PostgreSQL: его IP, пароль из `setup.ini` и имя базы отделения;
- `psql` на машине, откуда будете заливать данные (он есть на сервере; для Windows
  можно поставить клиент PostgreSQL).

## 1. Подготовка

1. Закройте старую программу, чтобы файл базы не менялся во время выгрузки.
2. Сделайте копию `DataBase.db` и положите ее в отдельный каталог. Все дальнейшие
   команды выполняются с копией, оригинал не трогаем.
3. Убедитесь, что база отделения на сервере уже создана и пуста
   (см. `server/debian/README.md` или `server/redos/README.md`, раздел
   «Несколько баз»). Заливать в базу, где уже есть случаи, нельзя: появятся
   дубликаты `id`.
4. Проверьте, что версия программы, в которую переносите, актуальна: схема
   PostgreSQL должна соответствовать `server/schema.sql` (346 столбцов).

## 2. Выгрузка из SQLite

Скрипт создает файлы рядом с базой, поэтому запускать его можно из любого каталога:

```bash
python3 /путь/к/server/migration/sqlite_to_csv.py /путь/к/DataBase.db
```

Если вы уже находитесь в каталоге `server/migration`, достаточно:

```bash
python3 sqlite_to_csv.py /путь/к/DataBase.db
```

Скрипт создаст рядом с файлом базы два файла:

- `cases.csv` — сами случаи, по одной строке на случай;
- `load_cases.sql` — команда `\copy` для загрузки и установки последовательности `id`.

В конце скрипт напечатает, сколько случаев выгружено и сколько поврежденных дат
было заменено на `NULL`. Это нормально: в старой базе встречались значения вроде
`2024--`, PostgreSQL такие даты не принимает.

Пример вывода:

```
Выгружено случаев: 1240 -> /home/user/old/cases.csv
Значений дат, которые были мусором и стали NULL: 3
Дальше: PGSSLMODE=require psql -h <сервер> -U pb -d <база_отделения> -f load_cases.sql
```

В папке `server/migration/` лежит `load_cases.sql.example` — это только пример
того, что генерирует скрипт. Для переноса используйте свой `load_cases.sql`,
созданный по вашей базе.

## 3. Загрузка в PostgreSQL

Файл `load_cases.sql` использует `\copy`, поэтому `cases.csv` должен лежать
в том же каталоге, из которого запускается `psql`. Проще всего скопировать оба
файла на сервер и выполнить загрузку там.

На сервере (Debian/Ubuntu или РЕД ОС):

```bash
PGSSLMODE=require psql -h 127.0.0.1 -U pb -d travma -f load_cases.sql
```

С рабочего места, где установлен `psql`:

```bash
PGSSLMODE=require psql -h <IP-сервера> -U pb -d travma -f load_cases.sql
```

`psql` спросит пароль пользователя `pb` (тот же, что в `setup.ini`). Чтобы
не вводить его каждый раз, можно задать `PGPASSWORD`:

```bash
PGPASSWORD='<пароль>' PGSSLMODE=require psql -h <IP-сервера> -U pb -d travma -f load_cases.sql
```

`travma` замените на имя базы своего отделения. В РЕД ОС с версионным
PostgreSQL `psql` может лежать не в `PATH`, а в `/usr/pgsql-<версия>/bin/psql` —
тогда укажите полный путь.

## 4. Проверка

1. Сверьте число случаев:

   ```bash
   PGPASSWORD='<пароль>' PGSSLMODE=require psql -h <IP-сервера> -U pb -d travma \
     -c "select count(*) from database"
   ```

   Число должно совпасть с числом случаев в старой базе (его печатал скрипт
   на шаге 2).

2. Проверьте несколько известных случаев: откройте программу, найдите пациента
   по фамилии, откройте старый случай, проверьте даты, диагноз, документы.

3. Проверьте, что новые случаи сохраняются: создайте тестовый случай, нажмите
   «Сохранить», убедитесь, что он появился в поиске. После проверки тестовый
   случай можно удалить.

4. Проверьте печать документа: документ должен появиться в `Output/`.

## 5. Если что-то пошло не так

- **`column ... of relation "database" does not exist`** — в старом файле есть
  поле, которого нет в новой схеме. Скорее всего, старая база новее или старше
  текущей версии программы. Не редактируйте `schema.sql` наугад: сначала
  выясните, из какой версии `DataBase.db`, и обновите программу/схему до
  совместимой версии.
- **`duplicate key value violates unique constraint`** — в базе уже были случаи
  или загрузку запустили повторно. Для чистого переноса нужна пустая база:
  создайте ее заново через `add_database.sh` (см. README своей ОС) и повторите
  загрузку.
- **`could not open file "cases.csv"`** — `psql` запущен не из того каталога.
  Перейдите в каталог с `cases.csv` или укажите абсолютный путь в `load_cases.sql`.
- **`invalid input syntax for type date`** — скрипт должен был заменить такие
  значения на `NULL`; проверьте, что выгрузка делалась этим скриптом, а не
  вручную.
- **Ошибка SSL/подключения** — проверьте `host`, `port`, `password` и что порт
  5432 доступен с машины. Подробнее — в README своей ОС на сервере.

## 6. Откат

Пока новая база не используется, откат простой: удалите базу и создайте ее
заново.

```bash
sudo -u postgres psql -c 'DROP DATABASE travma'
sudo bash server/debian/add_database.sh travma   # Debian/Ubuntu
sudo bash server/redos/add_database.sh travma    # РЕД ОС
```

После этого можно повторить загрузку. Если в базе уже работали врачи, не
удаляйте ее: сначала сделайте бэкап (`server/backup.sh`) и разбирайтесь
с ошибкой точечно.

## 7. После переноса

- Удалите `cases.csv` с рабочего места и с сервера: в нем реальные данные
  пациентов. Не отправляйте его в мессенджеры и не коммитьте в git.
- Оставьте `DataBase.db` в архиве на некоторое время, пока новая база не
  пройдет проверку.
- Настройте ежедневные бэкапы PostgreSQL (`server/backup.sh`) — в старой
  версии достаточно было копировать файл, теперь бэкап обязателен.
